1. Checkpoint Statement (finalized)

Ride Hailing creation and service-gating defects fixed. Ride creation now persists required order-item fields correctly, rides use order_type = transport, and transport acceptance / re-offering follows the correct service type. Targeted and full regression suites pass with zero failures. Ride business ownership remains a separate deferred issue.

2. Defects Found

Defect 1 - Ride creation never persisted

The ride order item was created with description and price, but neither is in OrderItem::$fillable, so mass assignment silently dropped both. The required product_name and unit_price columns (both NOT NULL) were never supplied. 

SQLSTATE[HY000]: General error: 1364
Field 'product_name' doesn't have a default value

Every ride booking failed with a 500. Because createRide() ran unguarded with no transaction, the parent orders row committed before the item insert threw, leaving an orphaned order.

Defect 2 - Wrong service type

The ride was stored as order_type = delivery instead of order_type = transport.

Both the accept gate and the re-offer path derive the gated service from that column: 

$serviceType = $order_type === 'transport' ? 'transport' : 'food';
return $rider_detail->current_service === $serviceType;

Consequences:

  • A ride-hailing rider accepting a non-COD ride resolved to ineligible.
  • Rejected / expired rides were re-offered to food riders.
  • TransportController::index and HistoryController filter on order_type = 'transport', so rides never appeared in transport history and instead showed under food.
  • The COD branch of the gate skips the service check entirely, so cash rides behaved differently from GCash / Maya / Card rides. The column fix makes both branches agree.

3. Finalized Decisions

D1 - Rides persist with order_type = transport
This is the canonical discriminator. It is the value every existing consumer already expected; writing 'delivery' was the defect, not the readers.
D2 - Order items use the real column names
product_name and unit_price. The previous keys were not fillable and were dropped without error.
D3 - Order + item + delivery commit atomically
Wrapped in a single DB::transaction so a partial failure can no longer leave an orphaned orders row. dispatchToNearest($delivery, 'transport') stays outside the transaction and is unchanged.
D4 - Auto-cancel coverage widened, not narrowed
AutoCancelUndeliveredOrder now uses whereIn('order_type', ['delivery', 'transport']). Rides only inherited this protection because they were mislabeled; the fix must not silently drop it.
D5 - No schema change and no data migration
SHOW CREATE TABLE orders confirms order_type varchar(255) NOT NULL DEFAULT 'pickup'. The text "delivery, pickup, dine_in" is a column comment, not an enum or CHECK constraint, so 'transport' stores without DDL. The development database holds 0 TRP-% rides, confirmed before and after a rolled-back live probe, so there is no legacy data to backfill.
D6 - Service gating was not weakened
Verified unchanged: the dispatchToNearest() candidate filter, the accept-time service gate, the COD acceptance branch, SmartDispatchService::scheduleDispatch() (its order_type !== 'delivery' early-return now correctly skips rides, which already dispatch directly and would otherwise have been re-dispatched to food riders after payment), the PaymentController post-payment dispatch hook, OrderRefundService (rides carry delivery_fee = 0), and the kitchen / preparation gates.
D7 - Ride business ownership stays deferred
createRide() hardcodes business_id = 1 and creates items without a business_id. This is not part of the service-gating fix and must not be mixed into this change unless the intended ride-ownership model is decided first.
